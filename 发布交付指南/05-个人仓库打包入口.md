## 手动触发一次完整发布

1. 打开个人仓库 Actions → **打包发布**（`.github/workflows/package-release.yml`）。
2. `Use workflow from` 选 **main**；`source_ref` 留空使用所选分支，或填写个人仓库内审核后的完整 40 位提交 SHA。
3. `version` 填个人仓库尚未占用的版本；留空读取源码版本，不会自动递增。已有 Release/草稿或指向不同源码的同版本标签会阻止发布。
4. `platforms=all`：Windows x64、Mac arm64、Mac Intel、Linux x64 四路并行。
5. `mode=release`：全部检查通过后自动发布 Latest。`draft` 仅保留草稿；`artifacts` 只保存 Actions 产物。
6. 完成后确认 5 个安装包（Linux 两种格式）加 BUILD-MANIFEST.json、SHA256SUMS.txt，共 7 个附件。

仅推源码不会触发打包。本次同步没有重新运行个人仓库的四平台构建，也没有复制公司 Release 附件；公司已有验收记录不能替代个人仓库未来运行的实际结果。

## 凭据和固定依赖

- 个人仓库的 prepare/publish job 已声明 `contents: write`，默认使用 GitHub 自带、限于当前仓库的 `GITHUB_TOKEN`。如另外配置 `RUIJIE_RELEASE_TOKEN`，会优先使用该 Secret。
- 公司仓库仍要求独立发布 Secret，不能用此个人仓库回退规则放宽公司的配置检查。
- Harness 来自公开的 `WYunS/ruijie-harness`，固定提交 `f48fe5cb09e37c1bcb4ed2c19f75ce5e1bf8aeae`（2.1.10），已确认该提交存在；Windows/Mac 分 CPU 准备和校验。Linux 不内置 Harness。
- 公司 Secret 不会随 Git 源码复制，本文和源码均不包含其明文。
- 更新元数据按当前 Actions 仓库生成，个人构建指向 `WYunS/OpenMausBot`。不要手改源码中的历史公司验收清单来冒充个人包的验证。
- 若 GitHub 组织/仓库规则限制 GITHUB_TOKEN 创建标签或 Release，应根据实际 403 检查规则或配置个人仓库的发布 Secret；不要关闭包完整性或安装验收门禁。

## 保留的验收门禁

Windows 验证最终 EXE 的实际安装、文件摘要、覆盖安装和卸载；两种 Mac 分别验证最终 DMG、安装后的文件/链接/权限/签名、运行依赖、替换和删除；Linux 验证 AppImage/DEB 及安装启动、升级行为。任一平台失败不发布整批。

Windows 未签名，Mac 为 ad-hoc 签名、未公证。真人账号、Finder/Gatekeeper/TCC 及真实历史用户数据升级仍按人工指南验收。
