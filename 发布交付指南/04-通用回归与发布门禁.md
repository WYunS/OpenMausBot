## 0. 本轮统一基线：这些旧要求不要再执行

### 0.1 本轮工作流与固定源码

使用公司 `0.1.86` 分支的工作流，source_ref 填本轮完整提交 SHA。公司 main 和原 0.1.85 tag 保持原指向。
流程修复后的构建 SHA 会晚于原源码 tag，禁止为省事移动该标签。
首次三平台构建当时选择 `platforms=desktop` 与 `mode=artifacts`；当前默认值见本文开头。
artifacts 模式直接固定当前 SHA，要求版本文件匹配，不创建远端候选提交；metadata_local 在每个 runner 中生成真实元数据。
其它发布模式仍保留来源/版本/资产检查，是否发布由本次所选 mode 决定。历史 v0.1.840 的版本排序不在本轮篡改。

原 Shared terminal smoke 引用未迁入的功能，现同一 YAML 改为 Desktop source checks：验证本地版实际支持的产品和发布接口。
未添加占位测试；此前缺少的固定 Harness 私库检出、缓存、两 CPU 准备与 Mac 签名/架构检查已接入。
仍应等实际原生 run 通过后交付，各平台未通过的日志必须保留。

| 旧指导或常见误用 | 现在的要求 |
| --- | --- |
| 只从 WYunS/main 打包，或认为公司 main 与本地相同 | 公司仓库选择维护者审核后的完整源码提交；个人镜像是另一条发行路径 |
| Bot Mac 必须交付一个 Universal DMG，两机器 DMG 哈希相同 | Apple Silicon / Intel 各一份 DMG，同版本、同构建源码 SHA，各有自己的哈希 |
| 修改独立 Harness 的 Universal 流程来减包 | 只拆 Bot 内置 Harness；独立公开 Harness 的源码、配置和 Universal 发行不动 |
| 用户先另装 Harness 2.1.6；打包不需要 Harness | Bot 内置固定 Harness，干净 runner 必须构建或验证缓存；用户无需另装 |
| 首先提供沙箱预置、manager URL 或共享账号 | 不打包沙箱预置；新 Bot 默认“这台电脑”，旧选择保留 |
| 所有内测构建先提交 24 小时内的人工放行 JSON | 企业候选入口不要求此正式发布回执；真实账号和安装验收在候选生成后完成 |
| Mac 每个 Mach-O 必须同时有两个 CPU | Bot 和内置 Harness 主程序必须是目标单 CPU；其他 native 文件必须兼容该 CPU，小型 Universal helper 可保留 |
| 缺 Developer ID、公证或 Team ID 就不能生成内测包 | 企业 Mac 为明确的 ad-hoc 内测包；完整签名仍须验证，不承诺正式公证或跨版本 TCC 保持 |
| 所有侧车都用发行者重新签名 | 企业流程保留固定 Harness / 飞书字节；其他组件按串行嵌套顺序签名 |

| 飞书必须先全局 npm 更新到截图所说的版本 | 按源码固定制品检查；截图中的版本/升级故障另查，不能临时 npm 更新掩盖包内问题 |

Bot 版本读取本次源码 `package.json`，不照抄旧指南的 0.1.73 / 0.1.84 / 0.1.840。

`2.1.10` / `f48fe5cb09e37c1bcb4ed2c19f75ce5e1bf8aeae`。

## 1. 维护者怎么更新公司工作流

### 1.1 先确认分支，不直接覆盖 main

2026-09-20 的只读审计发现公司 main 与近期打包修复分支
`fix/v0.1.84-package-release-auth` 已明显分叉，main 当时甚至没有 Harness 构建脚本。
这是当时快照，不把该分支名或旧 SHA 当成永久发布入口。
详细日志见 [公司打包审计](../docs/research/company-package-audit-2026-09-20.md)。

维护者在独立 `codex/...` 集成分支审阅配套改动，保留公司业务代码和已有打包修复；
不要整分支覆盖 main，不要仅挑 YAML 或四份指南，不复制开发者整个工作目录。
如基线差异过大，先协调唯一的发布源码，不能靠重试 Actions 补齐不存在的代码。

必须同步/核对的配套文件如下。已有且完全一致的文件无需重写，但不能漏交未跟踪的新脚本。

| 配套范围 | 必须一起核对的文件/目录 | 防止的失败 |
| --- | --- | --- |
| 企业入口和发布工具 | `.github/workflows/package-release.yml`、整个 `.release/`（含 toolkit、adapter、repository、Windows browser pin/fetch、平台 verify、测试） | 旧矩阵、缺平台支持、平铺 artifact 收集失败、发错仓库 |
| 构建配置与包内复制 | `electron-builder.enterprise.mjs`、`electron-builder.ruijie.mjs`、`electron-builder.yml`、`scripts/after-pack.mjs` | 缺资源只警告后继续打包、错误发行身份 |
| Harness 构建与识别 | `scripts/build-ruijie-harness.mjs`、`scripts/prepare-ruijie-harness.mjs`、`scripts/smoke-harness-bundle.mjs`、`shared/ruijie-harness-release.ts`、对应测试、`electron/desktop-runtime-layout.mjs`、`server/drivers/ruijie-harness-local.ts` | pin 不一致、重复构建、借用本机依赖、错 CPU |
| Mac 最终包装/签名 | `scripts/package-enterprise-macos-thin.mjs`、`scripts/enterprise-macos-sign.mjs` 及测试、`build/entitlements.mac.plist` | 签名顺序错误、仍调用旧 Universal 合并脚本 |
| 构建记录和 smoke | `scripts/desktop-build-receipt.mjs`、`scripts/check-ruijie-release-readiness.mjs`、`scripts/check-enterprise-package.mjs`、`scripts/smoke-feishu-package.mjs`、浏览器/服务端 smoke 及其 imports | 旧 UI/server、环境或账号要求混用 |
| 源码依赖与许可 | `package.json`、pnpm 锁文件/配置、构建脚本引用的 `electron/`、`server/`、`shared/`、`connectors/`、`third_party/`、资源及许可证 | “脚本有了但它引用的模块没带过来” |

此表是配套范围，不是独立的小型安装包清单：应交付审核后的完整 Bot 源码提交。
`dist-native`、`node_modules`、本地缓存、真实用户数据不作为源码补丁提交。
`.github/workflows/release.yml`、`package-win.yml` 若仍保留，须保留已补的 Harness token/pin/path，
但不要把它们作为本次企业内测入口；见第 2 节。

合入前在**目标发布检出目录**检查实际将要提交的内容，而不是只看本地文件是否存在：

```powershell
$ErrorActionPreference = 'Stop'
$PSNativeCommandUseErrorActionPreference = $true
$releaseSource = (git rev-parse HEAD).Trim()
git status --short
git remote -v
git ls-tree $releaseSource .release/toolkit
$required = @(
  '.github/workflows/package-release.yml', '.release/config.json',
  '.release/adapter.mjs', '.release/repository.mjs',
  '.release/toolkit/bin/release.mjs', '.release/toolkit/lib/core.mjs',
  'electron-builder.enterprise.mjs', 'scripts/build-ruijie-harness.mjs',
  'scripts/prepare-ruijie-harness.mjs', 'shared/ruijie-harness-release.ts',
  'scripts/package-enterprise-macos-thin.mjs', 'scripts/enterprise-macos-sign.mjs',
  'scripts/smoke-harness-bundle.mjs', 'scripts/smoke-feishu-package.mjs'
)
foreach ($file in $required) {
  git cat-file -e "$($releaseSource):$file"
}
git show "$($releaseSource):.release/config.json"
git show "$($releaseSource):.github/workflows/package-release.yml"
```

缺文件或 `.release/toolkit` 没有提交就先补齐；发布工具使用 Git 中的 toolkit tree SHA，
不能只把未提交文件拷进 runner。上述检查只是快速抓漏，不替代 imports、配置和测试检查。
目标必须包含 `windows-x64`、`macos-arm64`、`macos-x64`；默认配置还包含 `linux-x64`。

### 1.2 无安装器的同步检查

在独立检出、使用锁定依赖执行；这些命令不生成安装器，也不要求真人账号：

```bash
corepack pnpm install --frozen-lockfile
corepack pnpm typecheck
node --test .release/repository.test.mjs .release/toolkit/test/core.test.mjs .release/toolkit/test/tagged-release.test.mjs electron/enterprise-package.node-test.mjs electron/desktop-runtime-layout.node-test.mjs electron/ruijie-package-config.node-test.mjs scripts/check-ruijie-release-readiness.node-test.mjs scripts/enterprise-macos-sign.test.mjs scripts/smoke-harness-bundle.test.mjs
corepack pnpm exec vitest run scripts/build-ruijie-harness.test.mjs scripts/prepare-ruijie-harness.test.mjs scripts/cua-mac-arches.test.mjs server/drivers/ruijie-harness-local.test.ts server/browser-bundle-universal.test.ts
```

测试夹具不是 Mac 实际 codesign、公证或安装验收。不要调用 `release.mjs prepare` 冒充离线检查：
正常 prepare 阶段会访问 GitHub，并可能创建候选提交/分支。
独立的 `verify-ruijie-prerelease.yml` 是无安装器原生预检，可在另获运行授权后使用；
它也不生成正式发布凭据、不替代最终包验证。本次文档更新未运行这些工作流。

### 1.3 组织权限与构建输入一次准备好

- Node 由 `.release/config.json` 固定，当前 `24.20.0`；Bot 使用 `packageManager` 固定的 `pnpm@10.33.0`。
  Corepack 必须可用。不要用全局 pnpm 11、删除锁文件或换 Node 版本试运气。
  Harness 子仓库使用自己的 Corepack/Yarn，由 Bot 脚本调用；不要手工改其 packageManager。
- 公司 Windows/Mac job 检出 `AI-Applications-Team/ruijie-harness`，固定上面的完整 SHA并递归检出 submodule。
  使用仓库 Secret `RUIJIE_HARNESS_READ_TOKEN`，最小 Contents 只读，并确认组织/SSO 和所需子模块可访问。
  2026-09-20 已看到该 Secret 名称存在，但名称存在不证明权限、有效期正确。不得输出值。
  当前仓库的 `GITHUB_TOKEN` 不会自动拥有另一个私有仓库的读权限。
- 工作流 prepare/publish 使用当前仓库的 `GITHUB_TOKEN`；按 YAML 允许这些 job 的 Contents write、
  Actions artifact/cache、已固定的 Action 版本和所需 runner。无需给普通 build job 广泛写权限。
- `macos-15` 用于 arm64，`macos-15-intel` 用于 x64，`windows-2025` 用于 Windows。
  没有 Intel runner/额度须标组织环境阻塞，不能用 Rosetta 替代原生验收。
- Windows 浏览器由 `.release/fetch-windows-browser.mjs` 按 `.release/windows-browser.json` 下载，
  验大小、摘要和来源，再交给准备脚本。无需某位开发者的本地 vendor 目录。
  GitHub/Node/依赖下载网络须可达；不能关闭 TLS、哈希、许可或路径校验。
- 不需要沙箱密钥、个人模型/飞书凭据、Developer ID 或公证 Secret 来生成企业内测候选。
  不将任何账号、Token、Cookie、VPN 配置或真实用户数据写入源码、日志和安装包。

## 2. 选对入口和参数，避免再次走回旧门禁

| 入口 | 用途与边界 |
| --- | --- |
| `package-release.yml`，Actions 名称“打包发布” | 本次企业候选入口；用 `electron-builder.enterprise.mjs`，保留自动资源检查，人工验收单独记录 |
| `pnpm package:win` / `pnpm package:mac` | 仍走 `electron-builder.ruijie.mjs` 的正式品牌回执门禁；不是企业入口的快捷替代 |
| `package-win.yml` | 旧 Windows 流程仍调用 `pnpm package:win`，还有自己的时间/资源假设；不是本次免人工回执的企业流程 |
| `release.yml` / 旧 Universal 包装脚本 | 旧发布、更新桥、公证或合并路径；不用于本次两份内测 DMG |
| `verify-ruijie-prerelease.yml` | 无安装器原生检查，不负责打包、发布或真人授权 |

管理员完成源码集成并授权运行后，在
[公司“打包发布”](https://github.com/AI-Applications-Team/OpenMausBot/actions/workflows/package-release.yml)
选 **Run workflow**：

1. **Use workflow from**：选择包含新 YAML 的已审核分支。
2. **source_ref**：选择包含全部配套实现的源码提交/分支/标签。首次集成宜与工作流选同一审核分支并记录解析出的 SHA。
   选了新 YAML 却填写不含新脚本的旧标签，仍会失败。若界面没有新平台选项，先查工作流版本是否真的已同步。
3. **version**：留空读取源码版本；要改版本由发布负责人确定未使用的版本，不为了重试随便改号。
   已有匹配源码标签必须与检出 SHA、版本文件一致；不移动标签。已有该版本 Release（含草稿）会阻断，即使选 artifacts。
4. **platforms**：只打 Windows 选 `windows`；两种 Mac 选 `macos`；也可选 `macos-arm64` / `macos-x64`。
   `all` 还会构建 Linux；只交付 Win/Mac 不要因误选 all 被不需要的 Linux job 阻断。
   Windows + 两种 Mac 选 `desktop`；不支持填写 `windows,macos`。
5. **mode**：只取候选选 `artifacts`。界面默认是 `artifacts`。改选 `prerelease` 会创建并公开测试 Release；
   `draft` 会创建草稿。不要不看默认值就执行。

`artifacts` 不创建 GitHub Release，也不创建候选源码分支；直接使用已检出的源码 SHA。
版本文件必须已是请求版本。每个 runner 在编译前生成元数据，最终 manifest 和包内 metadata 应记录同一个 SHA。
原 0.1.85 tag 只是初始源码快照；本轮指定新的完整 SHA，不借用旧 tag 冒充新构建。
其它发布模式可能生成候选提交，仍需记录 prepare 输出；不同 SHA 的产物不可拼批。

## 3. 三层门禁分别负责什么

| 层级 | 企业入口实际检查 | 不证明什么 |
| --- | --- | --- |
| 源码/构建 | 配套文件、固定源码版本、依赖安装、源码测试、desktop-build 指纹及 UI/server 摘要、原生 staging | 不证明最终安装、账号或所有运行路径 |
| 最终候选自动验证 | afterPack 资源/哈希/许可；Harness 包内启动导出解析；飞书包内 Node/CLI 执行；浏览器及服务端 smoke；Mac 挂载 DMG 验签和原生 CPU | Windows 当前不自动跑安装向导；两平台都不完成真人 OAuth、TCC 或业务全覆盖 |
| 最终安装/人工放行 | 对确定哈希的安装包，在隔离系统账户完成本机工具、账号、数据、重启/升级等验收 | 不继承开发环境、旧包或另一 CPU 的通过结果 |

`dist-native/desktop-build.json` 是构建来源记录，企业入口也必须通过。
它和正式发布的 `release/verification/<target>.json` 不是一回事。
目前源码指纹包含四份指南和工作流；即使只改文档，旧构建记录也可能失效。
先定稿并提交交付内容，再构建/验收；不能只运行 `--write` 为旧 dist 补新指纹。
真正代码/资源变更须重新构建和验收，不能改时间或复制另一机器回执。

正式品牌配置目前仍要求 `REQUIRED_RELEASE_CHECKS` 全 passed、
对应平台、24 小时内、真实日志摘要、相同源码/浏览器/桌面构建摘要和 broker 地址。
此规则**未被本次文档改掉**。企业入口显式使用自己的 beforePack，是候选与正式验收分层，
不是删掉生产 hook；不得伪造 JSON、修改 status、放松哈希或改用上游配置来通过。
正式配置的 target 是 `win32-x64` / `darwin-arm64` / `darwin-x64`，
企业矩阵名是 `windows-x64` / `macos-arm64` / `macos-x64`，不要混填。

## 4. 每版保留的真实行为验收

所有变更操作在获授权的独立测试账户/fixture 中进行；源码服务测试遵循
[验证入口](../docs/verification/README.md)。禁止测试者操作开发者的真实 Bot、账号、聊天、远端电脑或全局 TCC。

- **身份/数据**：安装版服务数据为当前用户 `~/.ruijiebot`，开发版为 `~/.openmausbot`；
  Electron userData 是另一层目录。核对实际可执行文件与资源路径，不复制开发者加密凭据来“通过登录”。
- **默认电脑**：空配置连续新建两 Bot、退出重开再建一个，均默认“这台电脑”；
  已保存的其他电脑选择保持不变。实际用包内 CUA 截图、输入；只有真实操作触发接管，交还可继续。
- **Harness**：无单独 Harness、无开发 node_modules 的环境仍可使用内置运行时；
  使用测试者在 Bot 中登录的授权，后台按需运行，不无故弹独立 GUI。
  普通回复、工具、图片支持边界、取消/继续、凭据更新后的上下文分别检查。
  不把模型目录或账号额度永久硬编码成某个测试账户的结果。
- **浏览器**：面板先开/MCP 先用两种顺序；每种接管、导航、输入、交还、再由 Bot 操作三轮，
  正常链路连续观察至少 60 秒原连接。不以旧截图或重连后的新连接掩盖正常操作导致的断流。
  另测受控网络短断/后台恢复：有界重连、不重放操作、不夺取接管权。
  超时/拒绝连接用本地页面夹具；Google 不可达不等于打包失败。
- **搜索/语言**：确认模型操作与面板是同一 Bot/session 浏览器；
  验证无额外搜索 key 时声明支持的搜索、正文和来源，不偷偷回退 Firecrawl。
  中文普通回复、进度、英文工具输出后的总结、继续任务及用户要求英文的例外分别记录。
- **Windows 可见窗口**：冷启动、浏览器重启不出现多余终端；交互桌面测试是必需的，
  headless CI 和 `windowsHide` 单项检查不能代替。
- **插件**：网络/代理失败、HTTP 401、授权过期分别记录。
  离线首启→网络或系统代理恢复→点击重试→授权→一次只读调用→重启恢复；
  网络失败不能清除已有身份，绿色图标不是实时健康证据。
- **飞书**：按本包 `connectors/feishu/runtime-artifacts.mjs` 的 pin 验证 CLI/Node 与许可；
  当前仍为 CLI 1.0.93 / Node 24.15.0，不与构建用 Node 24.20.0 混淆。
  smoke 只证明本机执行，不证明授权、IM、服务端最低版本要求。
  用户截图中的 1.0.95 / 1.0.96、npm 下载超时及误报 unauthorized 尚待专案核查，
  本次未升级 CLI，也不能将其写成“已修好”。若当前服务确实拒绝固定版本，阻断飞书功能验收并报告。
- **UI/删除**：普通/窄窗口和系统缩放下控件可用、设置可关闭、长中文消息/工具输出可读；
  删除仅对临时 Bot，离线电脑不阻断本地删除，独立电脑不被顺带销毁；
  归档可恢复，重启后其他 Bot、连接与历史不丢。
- **Mac**：每个交付 CPU 独立完成 [真人验收](03-macOS真人验收测试指导.md)，尤其 CUA、飞书、
  麦克风/语音（如声明支持）、Keychain、同版权限稳定性和升级差异。
- **可选环境**：Local VM/Podman、云沙箱、外部模型或特定云插件缺账号/环境标“环境阻塞/未执行”，
  不是构建缺模块；不默认要求安装包自带 VM。若列入本版承诺功能，仍需补验或由负责人明确限制范围。

普通聊天、应用启动、核心工具、数据安全、资源完整性失败不能放行。
外部网络条件和非交付范围的可选环境不应让打包者盲目重打同一包。
不得把“自动检查过了”写成“所有账号/权限已通过”。

## 5. 失败时先查第一条错误，不要反复重打

| 最早失败信号 | 核查/处理 | 不应做 |
| --- | --- | --- |
| cloudflared 已 staged，随后临时目录 rm EPERM | 使用异步删除的有界重试；Node 24 同步删除设置 maxRetries 仍可能立即失败，真实 Windows 文件锁测试应通过 | 忽略所有清理错误，或关闭摘要和版本检查 |
| DMG smoke: Dependency escaped bundle | 对根目录和解析结果做 realpath，排除 /var 与 /private/var 别名；真实外链仍需阻断 | 删除包含关系断言或允许借用开发机依赖 |
| Missing release integration / Cannot find module（构建脚本阶段） | 检查 source_ref 对应提交是否真的含配套脚本及 imports、toolkit 是否已提交 | 只补一份 YAML 后反复重跑 |
| Harness checkout: could not read Username / prompts disabled / 403 | 检查只读 Secret 引用、授权范围、SSO、pin/submodule 访问 | 使用当前仓库 GITHUB_TOKEN 反复尝试跨私库，或输出 token |
| Electron 未下载、file: 锁文件变化、vendor-sidebar dirty | 使用配套 Harness 构建脚本；Windows 显式安装 Electron，runner 锁元数据稳定化后 immutable，保留已提交 sidebar | 删除锁文件、任意升级依赖、重建已提交 vendor-sidebar |
| Harness source has unexpected uncommitted changes | 新脚本仅允许已知生成图标；其他改动须审阅；已验完整缓存可复用 | 放行任意 dirty，或 reset 掉他人改动 |
| EMFILE / too many open files | 确认新 Mac 企业步骤的句柄限制和串行签名已同步；再看是否在 Harness 前置构建阶段失败 | 把日志中的 js.map 当成“文件不存在” |
| chrome_crashpad_handler / nested code not signed | 确认 Helpers/Libraries 先于框架、App；使用 thin 包装脚本 | 只给外层 App 盖章或关闭签名检查 |
| Source changed / UI or Server differs | 定稿当前提交并真实重新构建；不要把两批 dist 混用 | 只改 receipt 指纹或 verifiedAt |
| no verified ... receipt / feishu-live not verified | 先确认是否误用了正式 package:win/mac、旧工作流 | 为企业候选编造真人通过记录 |
| DMG staging already exists | 保留失败证据，在新的独立构建检出重试，或由维护者确认精确生成目录 | 删除整个工作区、用户 home 或缓存树 |
| Missing or duplicate platform manifests | 首先确认每个已选平台成功；collector 必须同时支持单 artifact 平铺和多 artifact 子目录 | 合并覆盖同名 manifest、删掉缺平台断言 |
| Artifact not found | 向前找首次 build/verify 失败；候选 pending 与已验证产物不同 | 当成新的运行时“缺模块” |
| 安装后真正 ERR_MODULE_NOT_FOUND | 保存版本/安装器哈希、缺失模块名、堆栈、实际资源路径，在包内复现 | 让用户全局 npm install 或借用开发 node_modules |

源码或工作流修复后，应从包含修复的审核分支重新发起一次新运行；
GitHub 的 Re-run 沿用原运行源码，不能验证后推的修复。仅原源码不变的瞬时下载/runner 故障才适合重试失败 job。
同一哈希候选只是验收器/环境问题，可以在保留证据后续验；产品或依赖字节变化就是新候选。
禁止拿不同版本、源码 SHA、toolkit SHA 或 CPU 的零散成功产物拼批。

## 6. 交付记录与放行

### 已通过产物转 Release（须有明确发布授权）

2026-09-21 用户在三平台产物验证通过后，明确要求发布到 Releases 页面。
工作流新增 `publish_existing_run`：留空仍走原打包；填写成功的打包运行 ID 则只执行 promote，不重编译。
此入口向维护者准备的 Release 草稿上传已验证文件；最后由有权限的维护者公开并设为 Latest。

本次选择公司 `0.1.85` 分支最新 workflow，填写 `publish_existing_run=35568352927`、
`source_ref=021c4455c4b3c96527e2b103ba12b3c534c9dbdc`、`version=0.1.85`。
使用 `v0.1.85` 关联实际构建提交；原 `0.1.85` 标签和 main 不移动。
先由已获授权的维护者创建指向实际构建 SHA 的 `v<版本>` 标签，再执行 promote。
公司 Actions token 虽有 Contents write，尝试同时创建旧构建提交的标签与 Release 曾返回 403；
预建精确标签后若创建 Release 仍返回 403，由已有权限的维护者先创建对应 SHA 的草稿，再运行 promote 续传。
公司 token 上传资产可行，但显式修改带正式标签的 Release 元数据同样返回 403。
因此公司 job 设置 `PROMOTE_UPLOAD_ONLY=true`，只验包和上传；维护者使用已有身份执行最终公开与 Latest 设置。
无需将个人访问 token 写入仓库 Secret。草稿按标签查询可能返回 404，入口会从 Release 列表定位同标签草稿。
桌面标签不再自动触发 npm/Docker；这两种独立分发保留原检查与显式 dispatch 发布能力。
入口复核原 workflow/run 成功、三个原生平台 manifest、聚合清单与实际安装包哈希，
先由维护者创建草稿，全部上传后核对 GitHub 返回的 SHA-256，再由维护者公开并设为 Latest。
已公开 Release 不覆盖；失败草稿只能在来源与已上传文件均匹配时续传。
Release 仍如实标明未签名/临时签名及真人验收边界，不发布自动更新 feed。

### 产物类型

0.1.86 起本轮整批交付采用 `all + release`：Windows、Mac arm64、Mac Intel、Linux x64 必须全部通过，同一源码、同一版本才汇总发布。Windows 最终 EXE 验证安装/覆盖安装/卸载；两种 Mac 最终 DMG 验证复制/替换/删除及安装目录文件和运行依赖；Linux 验证 AppImage/DEB 与安装后的启动、升级行为。不能将只通过 Windows 的候选解释为整批版本已通过。

- `candidate-<target>-<run>`：自动验收前的候选，manifest 为 pending，保留 14 天；不是通过包。
- `release-<target>-<run>`：该平台自动检查通过的包与平台 JSON，保留 30 天。
- `evidence-<target>-<run>`：诊断证据，保留 14 天；没有文件须看失败步骤，不假定所有阶段都会产出。
- `release-manifest-<run>`：所有选定平台收集通过后的 `SHA256SUMS.txt`、`BUILD-MANIFEST.json`。
- `release-preflight-<run>`：prepare 报告，供定位缺文件、源版本和输入问题。

新 thin 流程的历史 `intel` Universal 复验 job 应跳过；Intel 验证由 `macos-x64` 原生 build/verify job 完成。
“intel skipped”本身不是失败，但选了 macos 时缺 `macos-x64` manifest 仍必须失败。

报告至少包含：仓库、workflow 版本、输入 source_ref、最终构建 SHA、toolkit SHA、
Bot/Harness/飞书 pin、目标 CPU、工具版本、签名状态、包大小/最终哈希、自动检查与人工测试结果。
结果只用“通过 / 失败 / 环境阻塞 / 未执行”；证据去敏。
旧 Windows 本地预览、旧 Actions 发布恢复成功、单元测试和历史 2 GB DMG 不能替代新包实测；
新包大小必须实际生成后统计，不预承诺减到某个数值。

企业内测只交安装包和审计清单，不发布自动更新 feed；手动下载对应 CPU 安装包升级。
正式 Developer ID/公证、自动更新、生产推广需要另行授权和验证，不因本指南或 artifacts 成功自动获得放行。
