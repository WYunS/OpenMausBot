# 锐捷 Bot 对标 Grok Bot：调研结论与升级方案

汇报版｜2026-09-20｜核验代号：VERDE-0920-1615

本报告依据我们当前本地源码、这台电脑安装的 Grok Bot 0.30.0，以及同日已核查的 Grok Bot、OpenAI 官方资料。它不是照着截图猜架构，也不是承诺方案已经实现。

**当前状态：上一轮 UI 改动已按要求回滚。本报告只做调研和方案交付，不重新改代码、构建或部署。评估对象是保留既有本地改动的本地版本，不是老板仓库最新提交的重新整合版。**

## 先说结论：汇报时可以直接讲这段

我们与 Grok Bot 的主要差距，不只是界面好不好看，而是“用户不在线的时候，谁继续负责把事情做完”。

Grok Bot 的官方说明明确支持：用户关掉应用、合上电脑，后台工作和定时任务仍然继续。我们当前打开的是本地版，常规定时任务仍由本机上的程序负责，所以不能直接作出相同承诺。

但这不意味着要把现有产品推倒重做。源码里已经有远程工作区、自托管、定时任务、执行引擎和本机工具。建议先把现有能力用在一套长期在线的测试环境里，证明“用户关机，任务照常完成”；再补齐云端助手操作用户本机时的授权与接管；最后用真实任务决定 Harness、Codex 和不同模型怎么搭配，把更新和打包分开管理。

这是有源码基础的渐进升级方向，不是已经验收过的云服务。现阶段不承诺哪种引擎一定最好，不承诺闭源的 Grok Bot 内部具体用了什么，也不拿一次演示当作全面完成。

## Alpha｜调研确认了什么

### 1. 你说“关机后还会干活，说明任务不靠本机”，这个判断成立

Grok Bot 官方文档直接说明：关闭应用、笔记本或手机，不会停止后台任务和例行任务。[G1]

可以确认的是：这些工作不依赖用户的聊天窗口一直开着。

**不能继续推导成：所有模型、聊天记录、定时程序都装在同一台云电脑里。** 官方另外说明，对话放在电脑之外，应用授权凭据也有单独保存的位置；云电脑主要是助手使用浏览器、文件和应用的工作环境。[G2]

更准确的理解是：窗口负责与用户沟通，后台负责持续工作，云电脑提供干活的环境。它们可以分开，不必挤在同一个程序、同一台机器上。

### 2. 让用户点“更新电脑”，并不与云端运行矛盾

需要区分两件事：供应商更新自己的后台系统，以及更新用户正在使用的那台云电脑。

后一件事可能涉及重建工作环境。官方说明，这类更新会保留已同步的状态，但已安装的软件、包和正在运行的工作可能受到影响；备份没有准备好、助手正忙时，还会阻止更新。[G3]

因此，让用户选择时间，是为了避免突然打断工作，不是要求用户替供应商维护后台。

反过来，也不能说“不点按钮，远程电脑就永远不会被维护”。官方提到过时环境会重建，但我们没有查到可以据此承诺的统一强制更新时间。[G3、G4]

对我们的启发是：今后的更新提示，要说清“更新哪一部分、是否中断任务、保留什么、出问题怎么恢复”。

### 3. 没有模型选择器，不代表它背后只有一个模型

Grok Bot 的官方资料说明，模型选择由产品方管理，实际使用的模型组合可能变化。[G4]

所以我们可以借鉴它的简单体验：普通用户只需要说要做什么，不一定要先研究一串引擎名称。但不能据此断言它一定用了某个固定模型、Cursor 的某个内部引擎，或者两套独立的助手。这些闭源实现目前没有足够依据。

### 4. “聊天”和“干活”可以分开安排，不必强制换成两个大脑

你提出的方向是合理的：用户正在聊天，不应该成为后台任务能否继续的开关。

不过，这不要求每个位置都放一套大模型。一个在后台工作的助手，可以调用云电脑，也可以在获得授权后调用本机工具。需要更快的聊天响应或更强的复杂任务处理时，再考虑分别使用适合的模型。

**这是我们的设计建议，不是已经证实 Grok Bot 就这样实现。** 先把任务和窗口的关系理顺，比先决定“必须用几个模型”更重要。

### 5. “本地装了 Harness”和“模型在本地运行”不是一回事

可以把三件事分开理解：

| 名称 | 用人话说，它负责什么 |
| --- | --- |
| 模型 | 理解要求、判断下一步做什么 |
| Harness / Codex | 组织任务步骤，调用工具，处理执行过程 |
| 电脑工具 | 真正读写文件、运行命令、操作浏览器或鼠标键盘 |

把 Harness 放进安装包，只能说明这部分执行程序被带进来了，**不能说明模型权重也在本机，更不能自动保证断网可用或数据不出本机。** 如果它仍在调用远端模型，相关文字、图片等仍可能发送出去。

还有一个与当前源码直接有关的差别：**通过 Harness 选择 DeepSeek，与直接填 API Key 建一个聊天连接，不是同一种接法。** 我们当前通用 API-key 聊天路径没有同样的 Agent 工具接入，不能认为换个模型名称，就会自动具备电脑操作能力。[L4]

### 6. UI 的确存在差别，不能说“默认比例已经一样”

这次重新读了回滚后的源码，也重新检查了本机 Grok Bot 安装文件。关键差别是：

| 项目 | 我们当前本地版 | 本机 Grok Bot 0.30.0 |
| --- | --- | --- |
| 首次窗口 | 基础尺寸 1100×780，并最大化 | 普通启动路径为 1040×760，不主动最大化 |
| 手动调整后重开 | 保存了尺寸，但恢复时仍强制最大化 | 根据保存的最大化状态恢复 |
| 常规左栏 / 默认右栏 | 248 / 260 | 280 / 320 |
| 主要字号设置 | 界面 13，正文 14 | 对应刻度同样为 13、14 |
| 字体、回复样式 | 优先微软雅黑 UI，助手回复透明、段距更大 | 系统字体栈，灰底回复分组 |

这些是程序里的设置值，不是从手动拉过的截图上估算出来的。[L5、P1]

因此，“看起来不舒服”不能简单归因于字号。窗口恢复、三栏宽度、字体、段距、留白和消息分组都不完全一样。**实际页面缩放也没有在两款应用同时运行的统一条件下完成对照，所以不能声称视觉比例已经完全一致。**

窗口尺寸还涉及边框和内容区的区别；表中数字不是整张截图逐像素相等的证明。上一轮 UI 修改已回滚，以上是当前问题和后续评估依据，不是本次重新实施的内容。

## Beta｜我们的现状：有基础，但还缺哪一段

### 最重要的差别，是“现在谁在值班”

当前桌面入口会在本机启动 Bot 后台；常规定时任务由这个后台安排时间和发起执行。源码里的这一点是明确的。[L1]

因此，模型在网上、电脑在远端，并不等于未来所有定时任务都有人持续调度。某些已经交给外部执行端的工作可能继续，但本机关闭后，后续定时任务是否还有人发起，必须单独验证。

同时，仓库已有自托管和远程工作区路径，可以把后台放到长期在线的机器上。这说明第一阶段有现成基础，而不是先从零造一套云平台。[L2]

### 哪些能接着用，哪些需要补齐

| 目标 | 源码中已有的基础 | 还不能直接当成完成的部分 |
| --- | --- | --- |
| 用户关机后仍跑任务 | 后台、定时任务、远程连接、自托管路径 | 我们这套具体引擎、公司登录、工具和部署组合，尚未完成关机与故障恢复验收 |
| 从别的设备看进度 | 网页界面、设备配对、远程工作区相关实现 | 公司环境下的可访问性、权限和实际使用体验仍需验证 |
| 操作用户本机 | 本机电脑工具，以及可调用它们的 Harness/Codex 接法 | 云端助手如何安全找到并操作“这个用户的这台电脑”，需要补齐并验收 |
| 多种引擎可用 | 已有 Harness、Codex 等接入 | 没有同一批真实任务的对照数据，不能宣布谁全面胜出 |
| 缩小 Mac 安装包 | 本地已有按芯片拆分内置部分的打包改动 | 不等于公司远端和两种芯片安装包都已通过验收 |

### 本机控制不是简单把现有限制关掉

源码在远程连接模式下，会关闭部分本机控制、预览等能力。这是明确的保护措施：连接远程工作区，不应自动等于把自己的电脑交给远端操作。[L3]

后续应该在现有设备配对和工具基础上补齐授权关系，不是删掉限制，让所有远程请求直接进来。

### 可行性判断

**我建议走渐进升级，理由是现有源码已经具备可复用的底子。** 优先验证现有后台的常驻部署，再补齐具体缺口。

但它不是“换个地址马上就能稳定商用”。公司的模型登录、云电脑接入、用户数据隔离、断线恢复和版本配套，都还需要实际验证。特别是现在内置 Harness 的构建脚本主要覆盖 Windows/macOS，不能直接把它当成已经验收的 Linux 云端执行版本。[L4]

### 之前的安装问题，不要全部归到架构或 Mac 包上

“Harness 缺模块”“文件在但被误判不可用”“Mac 安装包太大”是不同问题。之前本地误判已经找到文件读取兼容问题，并保留了对应修复；这不能证明朋友的新电脑遇到的每一种缺模块错误都是同一原因。[L6]

Mac 同时包含两种芯片的内容，会影响体积，但不能凭这一点解释所有启动错误。新电脑安装、私有依赖下载、公司登录和实际任务仍应分别验收；云端升级方案不能替代这些检查。

## Gamma｜建议怎么推进，做成什么才算数

### 第一阶段：先证明“用户关机，任务照常完成”

**做法：** 优先利用现有自托管和远程工作区能力，准备一套长期在线的测试环境。先放一个工作区、一台隔离云电脑，以及一组无破坏性的任务，不先做复杂的大平台。

任务安排、进度和结果需要有持续保管的位置；不能只留在某次对话或一个临时执行进程里。云电脑重建，也不能顺带把重要记录一起弄丢。

**先用什么引擎：** 本地版继续保留现有 Harness；云端试点优先选能够在指定环境中独立启动、完成登录并调用所需工具的现有接法。Codex 是有官方自动执行文档的候选，但要通过公司的账号和工具验证；Harness 也可以参与，先把无桌面窗口运行和目标系统支持验证清楚。[O1、L4]

**验收看这几件事：**

- 用户提交任务后关闭客户端，任务仍在约定时间执行。
- 再用测试电脑真正关机验证，而不是只关窗口。
- 重新打开后，能看到真实进度、结果文件或明确的失败原因。
- 后台重启后，记录还在，不盲目重复已经可能完成的外发操作。
- 确认结果，而不只检查“任务已收到”或“程序没报错”。

依赖本机文件、只对本机开放的内网或本机鼠标的步骤，应提示等待设备上线，或在超时后失败。不能本机关机了，还宣称这些步骤也照常完成。

**这一阶段需要批准：** 测试环境、试点账号和数据范围、模型用量上限，以及谁负责看失败记录。资源和权限核清楚以后再给排期，不先报没有依据的日期。

### 第二阶段：再做到“授权以后，也能操作我的电脑”

**做法：** 在现有本机工具和设备配对基础上，补齐云端工作区与用户设备之间的受控连接。用户明确授权哪台电脑、哪些能力，助手才可以使用。

通常不需要为此再增加一个本机模型。后台助手可以通过受控连接调用本机工具；如果确实要求断网使用，再另行评估本地模型，不混着承诺。

**用户应该能看懂并掌握主动权：**

- 界面明确显示当前操作的是云电脑还是本机，最好显示设备名称。
- 读取文件、修改文件、运行程序和控制桌面分别授权。
- 高影响操作再次确认；先不开放付款、生产系统变更等高风险任务。
- 有随时停止和人工接管的入口，不让两个 Bot 同时抢一个桌面。
- 设备可以解绑，权限可以撤销；撤销后要真正阻止后续动作。
- 离线、休眠、锁屏时清楚提示限制，不绕过系统保护。
- 如果文件内容或截图需要发给远端模型，应事先说明，不能把“本机执行”宣传成“数据绝不外发”。

**验收：** 允许的任务能做，拒绝的任务做不了；中途撤权能生效；断网后不会假装完成；重新连接不会错误换到别的电脑。

关闭聊天窗口后能否继续本机工作，取决于是否另外保留一个用户知情、可关闭的后台连接端。整机关机后，本机操作仍然不可能继续。

### 第三阶段：用实际效果选引擎，把更新和打包理顺

**引擎不要先定输赢。** 用同一批任务、相同权限和相近环境比较候选组合。看完成率、误操作、人工接管、耗时，以及完成一件事的总费用。

例如先选约 20 个代表任务做筛选：资料整理、文件处理、浏览器表单、多步骤操作等。它只是第一轮评估，不能把 20 个测试当成所有场景都可靠。

**模型可以分工。** 简单问答和摘要优先考虑经济型模型；复杂视觉操作、长步骤任务，交给经过测试的更强模型。不先认定某个 DeepSeek 型号一定便宜、一定能做或一定做不了，也不把聊天连接的能力当成 Harness 接法的能力。

更贵模型的使用范围和费用上限要明确。成本应按“成功做成一件事”算，而不只比较一次调用的价格。

**更新分清对象。** 桌面界面、执行引擎、云电脑环境、本机连接端，应分别说明版本与更新影响。分开升级不等于随意混搭，需要列出经过验证的配套组合。

**Mac 拆包保持前面的方向。** Bot 内置的 Harness 随 Apple 芯片、Intel 芯片分别准备；单独给用户下载的 Harness 通用版可以继续保持原有策略。实际能省多少体积、两类新机器能否正常安装，以产物测试为准。不要为了升级云端，把稳定的独立 Harness 发布流程一并推翻。

**验收：** 用没有开发环境的新电脑验证安装、引擎启动、登录和真实任务；再验证升级后的数据保留。公司远端没有实际跑过的项目，就标为未验证，不能用本地成功代替。

**依赖和令牌提前说清楚。** 下载私有依赖的令牌，是构建机取材料的钥匙；发布、签名所需的凭据，是把安装包正式交付出去的证明；模型与飞书授权，则是用户运行时调用能力的权限。它们不能相互替代，也不应随手写进源码或安装包。具体名称和配置按四份打包指导及公司仓库约定执行，缺什么应在打包前明确提示，不等流程跑到最后才发现。

### 三个阶段的先后关系

建议先完成第一阶段的持续执行演示，再开放第二阶段的本机权限；第三阶段的候选引擎小测试可以提前做，但不因为选型讨论不断替换当前稳定版本。

UI 是独立的一条线。以后如果重新启动 UI 工作，先用同样的窗口、缩放和内容确认效果，再改一个小范围；这份方案不授权重新开启已经回滚的那轮修改。

## 汇报时不要说过头的几句话

可以说：我们有源码基础，建议分阶段验证和升级。  
不要说：我们已经具备与 Grok Bot 一样的完整云端能力。

可以说：Grok Bot 官方确认关机后后台任务继续。  
不要说：我们已经知道它所有服务部署在哪台电脑、用了哪一个 Harness。

可以说：当前源码的本机工具可以复用。  
不要说：随便接一个模型，就能可靠、安全地控制宿主机。

可以说：内置 Harness 可以按目标芯片准备。  
不要说：安装包一定减半，或者远端打包一定不会再缺依赖。
