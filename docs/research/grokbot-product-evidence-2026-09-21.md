# Grok Bot 产品承诺与架构边界：本轮第一方核查

核查日期：2026-09-21。用途：为产品方向与下一步架构决策提供证据，不推测闭源进程布局。本轮只新增此笔记，未修改代码、配置或运行应用。

## 核查范围与可信度

已读仓库 `AGENTS.md`；本任务不涉及服务或会话变更验收。2026-09-20 的研究仅作寻址线索，下列产品事实均在本轮重新获取官方正文。请求使用 Windows `curl.exe` 8.21.0 / Schannel，保留正常 TLS 证书校验，六个 Grok Bot 页面与一个 AWS 对照页面均成功返回，curl exit code 为 0。最初 Python urllib 的请求因本地 CA 链缺失失败；后续使用系统信任库成功，未使用 `-k`、`--insecure` 或禁用校验。

这些资料证明厂商当前公开承诺，不等于独立产品实测，也不保证用户安装的旧版本均有同样功能。页面未提供逐版本历史，因此正文不将当前文档回填为旧版本事实。

## 一、应对标的产品承诺

Grok Bot 的核心不是远程桌面或模型选择器，而是用户可以长期委托工作的 Bot：有名字、职责、对话、逐步积累的上下文，并能在真实工具中完成任务。G1 原文：

> AI teammates with names, jobs, and context that compounds over time.

公开资料把交互、持续工作、状态积累和审批贯穿在同一个 Bot 身份中。对我们而言，“同一个助手”首先应是身份、任务和承诺连续，而不是保证所有步骤只调用同一个模型。这是产品解释，不是 Grok 内部实现事实。

| 用户关心的承诺 | 本轮确认的官方行为 | 不应扩张成的结论 |
| --- | --- | --- |
| 笔记本关闭后继续工作 | G1 明确背景 turn 与 routine 不随关闭 app、笔记本或手机停止；G5 再次确认云端例行任务 | 任何依赖本机文件、内网或界面的步骤都能在关机后完成 |
| 隔天仍是同一个助手 | G1/G2：Bot 保存稳定偏好、事实与工作摘要；同一 Bot 可从桌面和 iOS 访问 | 所有历史消息会无限装入每次模型上下文；记忆永远正确 |
| 有可延续的工作环境 | G1/G2：账号内 Bot 共享持久云电脑文件、浏览器与登录；各 Bot 有自己的屏幕 | 每个 Bot 都有隔离操作系统；屏幕是安全隔离边界 |
| 随时干预工作 | G2：用户直接消息优先于后台工作，可改变当前 turn 方向；停止不撤销已完成动作 | 打断可以回滚外部已发送消息或已修改数据 |
| 自动化能被检查 | G5：routine 有名称、指令、何时运行、启停和运行历史；测试会执行真实工作 | 保存等于立即运行；已受理等于任务已完成 |
| 不让用户选模型 | G3/G4：Cursor 管理模型选择，界面没有模型选择器 | 内部始终只有一个模型，或必定是某个固定厂商 |

G1 关机承诺短引文：

> Closing the app, your laptop, or your phone doesn't stop a background turn or a routine.

G2 对结果的要求也值得对标：链接、文件、可核查的来源、已做与待批准动作、未解决的问题都出现在交付中。这里的差异化价值是可委托且可检查的工作，不只是聊天质量。

## 二、“后台托管任务”和“直接放在远程电脑”有哪些已知与未知

### 已知事实

1. **会话不与云电脑同生共死。** G6 明文：`Conversation history is stored outside the computer`。更新、恢复、重建电脑不直接删除聊天。G2 同样说明对话在电脑之外。
2. **连接器凭据不放在工作电脑。** G2/G4：OAuth token 保存在 Cursor connector backend，Bot 调用工具而不获得 token。G4 原文：`tokens are never stored on the computer`。
3. **电脑是可休眠、可替换的工作环境。** G4：`Idle computers hibernate automatically.`；过时系统镜像会重建且保留成员文件。G6 描述已同步数据的持久副本与恢复。
4. **任务有独立于聊天口头承诺的触发记录。** G5 定义下一次匹配时刻、启停、测试、运行历史、Webhook 受理状态等明确行为。
5. **公开文档确实提到服务端 routine 模式。** G5 的 “this Bot keeps its routines on the server” 表示该 Bot 的 routine 存在 Cursor servers，此时面板不可编辑名称、指令、时间，也不能从面板启停/删除/测试，需在聊天里让 Bot 修改；面板仍可看触发摘要和运行历史。
6. **公开文档出现控制服务，但未披露任务内部拓扑。** G4 将部分管理动作称为 `Grok Bot control-plane actions`，并说明生产 control plane 有每日加密备份。这支持管理状态与工作电脑具有不同职责，不能据此确认具体 Scheduler、Worker 或数据库布局。

### 决策可用的推断

- “任务是否被可靠接收、未来何时触发、当前完成到哪、交付物在哪里”与“本次在哪台电脑执行”应在产品合同中分开。云电脑重建时前者应仍可查询；无需规定第一期一定拆为不同机器或微服务。
- 单台远程电脑常驻调度器可以达到本机关机仍执行。其局限不是“不算云”，而是如果计划、运行状态与执行盘共同故障，任务的恢复和解释能力受同一故障影响。外部持久状态、备份与恢复机制补上后，仍可成为合理的早期部署。
- 只有需要浏览器、桌面、文件环境的步骤才必然需要电脑。API 类工作可设计为无需唤醒完整电脑；这是我们的成本与可靠性选项，不能写成 Grok 已证实做法。

### 重要反证与未知

G6 原文：

> A bot cannot finish a turn while the computer says Reconnecting or Couldn't Reach Grok Bot's Computer.

因此，**“聊天保存在电脑外”不能证明 Grok 的推理、对话响应或 Agent 循环能脱离云电脑继续运行。** 它的实际产品仍可能把完成 turn 的可用性与电脑紧密绑定。我们如果选择电脑故障时仍能解释状态、接受新委托，这是明确设计的产品能力，不应作为“复刻其架构”的既知事实。

G5 的服务端 routine 提示只说明一种用户可见管理模式，不足以判断普通 routine 是否存在 VM 内 cron、后端集中 Scheduler 或双重机制。没有资料证明关机前后会在本地与云端热迁移 Agent。

## 三、模型与执行引擎：公开资料能裁定到哪

G4 原文：

> Cursor manages model selection. There is no customer-facing model picker, and the serving mix can change over time with no fixed vendor set guaranteed.

G4 还说用量分析展示实际服务每次请求的模型，包括 failover，计费依实际服务模型。

**事实：** 产品封装了模型选择，并预留服务组合变化与失败切换。**不能确认：** 是否按任务难度、视觉需求、时延或成本动态路由；是否有“聊天模型＋执行模型”的固定双模型结构；是否使用 Codex、锐捷 Harness 或具体私有引擎。

另一个容易混淆的事实：G4 明确 Auto Review 使用 `an independent review model`，覆盖 shell、插件、computer use、routine 写入和委托等风险动作。这只能证明存在独立审批评估模型，不能证明主任务由两个聊天 Agent 协同。

对我们的决策启示：应先定义一个 Bot 身份和统一任务记录，再允许后台换用模型能力。是否要两个长期独立的聊天 Agent，应由离线、隐私或本地自治需求证明；不应因为同时操作云电脑和宿主机就自动增设一个本地聊天模型。

## 四、本机控制的真实范围与边界

G4 对本机的直接描述：

> run commands, read files, and move files between the cloud computer and the local machine.

G2/G3/G4 一致说明：通过桌面 app 执行，本机与云电脑分开授权，默认逐命令批准，设置只适用于当前桌面；本机控制与云电脑内 Auto Review 并非同一控制。

这些资料证明本机命令和文件能力。**没有足够证据把它扩写成任意宿主机 GUI、锁屏或登录界面的全面控制。** 若我们的产品承诺宿主机 GUI 自动化，应单独纳入能力建设与验收。

G4 允许成员把云电脑流量经桌面转发，使用桌面的网络和 IP。因而依赖本机转发才能访问的公司内网会受设备在线状态影响，这是架构推断，不是本轮断网实测。

云任务与本机执行并不冲突，但必须在用户旅程中明确：本机离线时，哪些步骤可以继续、哪些等待、何时超时、是否需要重新审批。不能以统一聊天界面掩盖执行目标差异。

## 五、为什么云电脑仍需要“更新”

G3 区分客户端更新与 Agent Computer 更新。G6 给出清晰的环境生命周期：

| 操作 | 已公开行为 | 用户需要知道的影响 |
| --- | --- | --- |
| Update | 移至最新电脑版本，可现在或稍后执行；保留已同步 Bot、文件、登录 | 安装的软件包被移除；无法暂停的 turn 可能被丢弃 |
| Recover | 重建电脑并重新连接；保留 Bot、文件、登录 | 安装的软件包被移除 |
| Reset | 恢复上次快照并建立最新版本电脑 | 运行工作中断；快照后未同步 Bot/文件可能丢失；安装的软件包被移除 |

G6 的 `Backup not ready` 表示等待安全备份，`Agent busy` 表示 Bot 未能及时暂停所以此次未更新。这不是要求用户维护厂商所有后端服务，而是让有状态工作环境的重建遵守数据和任务边界。

产品设计启示：更新应回答“何时中断、保留哪些状态、移除什么、如何恢复”。不应只显示一个含糊的“后台更新中”。如我们希望安装依赖长期稳定，可引入声明式软件环境重建，但这是我们的新增设计。

## 六、定时任务已公开的精确语义，可直接转成需求讨论

- G5：时区取设置中的 `Timezone`；可以自动检测或固定选择。工作日为周一至周五。
- G5：保存不立即运行。例如 08:05 保存每天 08:00，不补当天 08:00，等下一次匹配时刻。
- G5：routine 不启用就不触发；测试立即执行真实任务，可能修改文件或调用连接工具。
- G5：每 Bot 最多 50 个 routine，界面保留最近 20 次运行记录。这些是对标产品的限制，不应直接照搬为我们应有的容量。
- G5：Webhook 的 200 表示已接受调用并开始一次运行，**不表示指令已完成**；结果需看运行历史或会话。
- G5：高频触发消耗预算；应先缩小频率和事件匹配范围，再考虑提高预算。保存但不触发不消耗运行用量。
- G2：长期未使用后，产品可能询问是否继续 routine，未回复则暂停。因此“云端常驻”不是“所有自动化永久无条件运行”。

没有公开确认的边界包括：运行重叠策略、服务中断补跑窗口、夏令时重复时刻处理、重试幂等保证、任务截止时间与最长期待。这些需要我们的产品主动决定，不能写成已经从 Grok 抄得的规则。

## 七、一个有用的对照：集中触发不等于集中执行

A1 将 EventBridge Scheduler 定义为集中管理调度的服务，目标可以是 SQS、SNS、Lambda 等；提供一次性与周期调度、重试次数、失败触发保留时间。

原文：

> EventBridge Scheduler provides at-least-once event delivery to targets

这说明“可靠地在时间到达时发起工作”与“目标把业务任务完成”是两个不同责任。它也说明重试投递可能产生重复，不能把调度受理当成外部业务副作用只执行一次的保证。

**仅作为设计参照：** 我们不因此需要采用 AWS，更不能断言 Grok 使用这套机制。对当前产品最有价值的是：调度记录、执行派发与完成结果应可区分；外部写操作重试前需去重或核对已完成效果。第一期仍可在一个服务部署中实现这些职责。

## 八、可供方案引用的判断

1. 对标方向可表述为“一个可长期委托、跨设备交流、能够使用真实工具并留下可核查结果的助手”。这比“给用户一台装了模型的远程电脑”更完整。
2. 云端定时不必一开始建复杂平台。先保证客户端关闭后计划仍有人持有、到时有执行者、机器故障后状态可解释与恢复；物理合部署与否是次一级选择。
3. 同一个 Bot 不等于同一个模型。公开事实支持封装模型并变化服务组合，不支持猜测固定双模型结构。
4. 已知事实足以支持区分会话记录、连接器凭据和工作电脑；不足以还原 Grok 私有 Agent 循环位置、调度器拓扑及 Harness 品牌。
5. 本机控制必须作为明确授权的执行目标设计，不能由“云电脑可用”推导“宿主机自动可控”。
6. 方案应逐项写明：官方事实、我们的设计决定、需要用源码/试点验证的假设。闭源未知处允许有判断，但不能换成伪事实。
