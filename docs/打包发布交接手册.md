1. **正确入口是 Actions 中的「打包发布」**，文件为 `.github/workflows/package-release.yml`。不要误用英文 `Release`、`Package Windows`、`Package Ubuntu`，也不要把 npm、Docker 流程当作这次企业安装包入口。

## 3. 账号、权限与接手环境

### 3.1 已有管理员 PAT 和密钥，实际怎么使用

正常操作不用重新设置 Secrets：用同事已有、对目标仓库有权限的 GitHub 身份登录，直接运行 workflow。若 CLI 尚未登录，执行 `gh auth login --hostname github.com`，在交互界面选择已有 token；不要把 token 写进命令参数、源码或本文。`gh auth status` 显示的是 CLI 当前身份，Git 的凭据管理器可能另存了其他账号；“有超管 PAT”不等于当前命令正在用它。遇到 403 先核对目标仓库和实际身份。

两枚公司 Secrets 是 workflow 的凭据，个人电脑上的 gh 登录是人工操作的凭据，二者不会自动相互同步。管理员 PAT 可用于维护仓库或更新 Secret；Harness 读取凭据负责跨私库只读检出，不用拿它执行发布。

| 凭据 / 权限 | 用途 | 接手检查 |
| --- | --- | --- |
| 同事自己的 GitHub 账号 | 浏览 INTERNAL 仓库、查看 Actions/Release、提交源码和手动触发 workflow | 组织成员资格、仓库权限、组织 SSO/企业策略、Actions 额度 |
| `RUIJIE_RELEASE_TOKEN` | prepare 创建候选提交/引用，publish 创建草稿、上传附件、发布 Release/标签 | 在公司 Bot 仓库可用；当前流程要求 Contents 与 Workflows 读写。设置 Secrets 的管理员另需 Secrets 管理权限 |
| `RUIJIE_HARNESS_READ_TOKEN` | 检出另一个私有仓库 `AI-Applications-Team/ruijie-harness` | 对固定源码及所需私有子模块有只读访问；至少 Contents Read |
| 自动 `GITHUB_TOKEN` | 本次仓库内 Actions 操作，以及 artifacts 模式的仓库 API 访问 | 自动生成；不能假设能跨私库读取，也不要替回曾发生 403 的发布链路 |

如果使用 fine-grained PAT，通过 CLI 触发/重跑/查看 Actions 还需相应的 Actions 权限。组织策略和规则集会影响 PAT，持有一个“超管”密钥不等于所有 GitHub API 都自动放行。

现有 Secrets 已经支持本次成功发布，无需为了交接再次覆盖。接手时记录实际持有人、到期时间、组织授权状态；只有确需换持有人、到期或报错时才用已交接的管理员权限更新。**Secret 已保存并不保证原持有人离职后仍可用。** 若公司要求改为服务账号或新维护者凭据，更新同名 Secret 即可，不需要把密钥写到 YAML。GitHub 不能读回 Secret 明文；应从正式凭据交接渠道取值或替换。

下面命令只显示 Secret 名称与更新时间，不显示密钥值：

```powershell
gh auth status
gh repo view AI-Applications-Team/OpenMausBot --json nameWithOwner,visibility,defaultBranchRef
gh secret list --repo AI-Applications-Team/OpenMausBot
```

必要时在仓库 Settings → Secrets and variables → Actions 更新同名 Repository Secret。也可使用以下交互输入方式，密钥不要写在命令参数里：

```powershell
gh secret set RUIJIE_RELEASE_TOKEN --repo AI-Applications-Team/OpenMausBot
gh secret set RUIJIE_HARNESS_READ_TOKEN --repo AI-Applications-Team/OpenMausBot
```

## 4. 下一版本怎么发：网页操作优先

本节命令默认用于公司仓库。若维护个人副本，仓库参数改为 WYunS/OpenMausBot，workflow 分支改为 main；其发布令牌逻辑见个人打包说明。不要把本地 gh 的当前账号或 Git 的 origin 名字当作目标仓库的自动证明。

### 4.1 选择流程版本和源码

打开 [打包发布](https://github.com/AI-Applications-Team/OpenMausBot/actions/workflows/package-release.yml)，点击 **Run workflow**。

“Use workflow from”决定用哪一版 YAML；输入的 `source_ref` 决定检出哪一版应用源码和 `.release` 脚本。它们是两个不同控制项。只选新 YAML、却把源码指定到缺少配套脚本的旧提交，仍会失败。

初始交接基线使用 `Use workflow from = 0.1.86`。如果后续源码在新分支继续维护，需让该分支同时包含本次完整集成，再选它。未来是否把发布线合入 main 由团队评审决定，本轮没有替团队做合并。

### 4.2 输入参数

| 字段 | 推荐 / 含义 | 容易踩的坑 |
| --- | --- | --- |
| Use workflow from | 初始用 `0.1.86` 分支 | 不要误选默认 main 或历史标签 |
| `source_ref` | 已审核的完整提交 SHA；留空使用 workflow 分支 | 分支会变，使用完整 40 位 SHA；短 SHA 会被 checkout 当作分支名；必须包含配套源码 |
| `version` | 下一个尚未发布的版本，例如 `0.1.87` | 例子不是自动保留的版本，先确认未占用；留空只是读 package.json，不会自动加一 |
| `platforms` | `all` | `desktop` 仅 Windows + 两种 Mac，不含 Linux |
| `mode` | 正常自动发版用 `release` | 全部选定平台通过后直接发布，没有等待人工点击的暂停点 |

其他平台选项：`windows`、`macos`、`macos-arm64`、`macos-x64`、`linux`。选择子集时只要求该子集通过；如果用 `windows + release`，也会发布只有 Windows 的版本。需要四平台齐全的正式交付必须选 `all`。

| mode | 完成后的状态 | 适用场景 |
| --- | --- | --- |
| `release`（默认） | 正式 Release，Latest | 已建立验收信心的正常发版 |
| `prerelease` | 预发布，不设 Latest | 如 `0.1.86-beta.1`；含预发布后缀不能选 release |
| `draft` | 已验证附件上传到草稿，不正式发布 | 首次四平台验证、需要先做真人验收 |
| `artifacts` | 只保存 Actions 产物，不创建 Release | 纯构建测试；源码 package.json 版本必须与 version 一致 |

**四平台全流程已在本轮实跑成功；同事首次独立接手仍建议用新版本、`all + draft` 演练。** 检查、真人验收后发布同一草稿，操作见第 7 节。自动 release 路径并不替代真人登录、安装耗时和系统权限验收。

`artifacts` 模式不会帮你生成新版本候选提交；例如源码仍为 0.1.85，填 0.1.86 会被版本一致性检查拦截。先在源码中正确提交新版本，或用 draft/release 模式的候选版本功能。artifacts 完成后再运行 release **会重新构建**，不是对原产物的自动晋级。新实现允许 artifacts 重用已发布的显示版本用于修复候选；它不检查/改写旧发布标签，不创建 Release，manifest 必须标明本次新 SHA。正式发布仍必须使用未占用的新版本。

### 4.3 正常执行与下载

1. 确认版本没有现有 Release 或草稿占用，源码和 workflow 都已推送到公司仓库。
2. 填好参数，点击 Run workflow。记录 Run URL、源码 SHA、版本和目标平台。
3. 看 `prepare` 是否通过，Summary 中会写明四个平台实际共用的最终构建 SHA。
4. 等待 build 矩阵结束；每个平台单独显示状态，其他平台失败不会立刻取消仍在运行的平台。
5. 所有选定平台成功才进入 `publish`。检查最终发布步骤，不能只看 build 变绿。
6. 打开 Releases，检查标签、可见状态、Latest 标记、附件数和 `BUILD-MANIFEST.json`。`all` 正常应有 5 个安装包 + 2 个审计文件，共 7 个附件。
7. 在对应系统下载安装，补做第 8 节列出的真人验收。保留 Run 和 Release 链接用于追溯。

新版本通常不用手工先打 tag；发布时使用 `v<version>` 标签并指向实际构建提交。若已经预建标签，只有源码提交和版本完全一致才允许复用。发布过的版本不覆盖，不强推移动历史标签。

### 4.4 CLI 方式（这些命令会触发真实构建）

以下是未来维护者的操作示例，本次编写文档没有执行。`$SourceSha` 必须替换为审核过的真实提交；版本先查占用。

```powershell
$Repo = 'AI-Applications-Team/OpenMausBot'
$WorkflowBranch = '0.1.86'
$SourceSha = '替换为审核过的40位源码提交SHA'
$Version = '0.1.87'
gh workflow run package-release.yml --repo $Repo --ref $WorkflowBranch -f source_ref=$SourceSha -f version=$Version -f platforms=all -f mode=release
gh run list --repo $Repo --workflow package-release.yml --limit 5
```

从上条输出找到自己的 Run ID，再观察，不要误重跑别人的任务：

```powershell
$RunId = '替换为本次RunID'
gh run watch $RunId --repo $Repo --exit-status
gh run view $RunId --repo $Repo --log-failed
```

## 5. Workflow 内部如何工作

整体流程：手动触发 → prepare 校验并固定源码 → 四平台并行 install/build/verify → 汇总 manifest 和 SHA256 → 创建并上传草稿 → 再验证远程附件 → 正式发布 / 预发布 / 保留草稿。

### 5.1 prepare：先失败，避免白跑大包

- 检查发布凭据；Windows/Mac 还检查私有 Harness 读取凭据是否配置。
- 读取并校验版本，分页查找现有 Release **及草稿**；相同版本占用时停止。
- 检查配套脚本、包管理器版本、Windows 浏览器 vendor 的可访问性等。
- artifacts 模式或匹配的已有源码标签：保持检出的 SHA，不改版本文件。
- 无现成标签的 draft/release/prerelease：必要时经 GitHub API 生成版本和构建元数据提交，放在 `release-candidates/v<version>-<runId>-<attempt>`。**不回写 main 或输入源码分支。**
- 输出最终 SHA、版本、Node 版本、平台 matrix。后续全部检出这个 SHA，不能把初始输入 SHA 当作最终构建 SHA。

包版本当前只在 `.release/config.json` 的 `versionFiles: [package.json]` 中声明。未来新增其他版本文件时要同步配置；候选提交的版本更新也不会自动帮团队推进主开发分支版本。

### 5.2 build：四个原生平台

| matrix target | GitHub runner | 安装包 | 随包 Harness |
| --- | --- | --- | --- |
| `windows-x64` | `windows-2025` | `RuijieBot-版本-setup.exe` | 固定 2.1.10，Windows x64 |
| `macos-arm64` | `macos-15` | `RuijieBot-版本-mac-arm64.dmg` | 固定 2.1.10，arm64 |
| `macos-x64` | `macos-15-intel` | `RuijieBot-版本-mac-x64.dmg` | 固定 2.1.10，x64 |
| `linux-x64` | `ubuntu-24.04` | 一个版本化 AppImage、一个版本化 DEB，名称以 manifest 为准 | 当前不内置 Harness |

并行上限 `max-parallel: 4`，`fail-fast: false`。这是允许四个同时跑；组织额度或 runner 供给不足时仍会排队。prepare 超时 10 分钟，单平台 120 分钟，publish 30 分钟。

各平台安装 Bot 的 frozen-lockfile 依赖，准备原生资源，然后通过 `.release/adapter.mjs` 执行构建和验证。所有运行器重新生成反映最终 SHA 的构建元数据，避免版本候选提交后仍写旧 SHA。

Windows 另有两层安装检查：构建前的小型真实 NSIS 回归；构建后在 GitHub-hosted 临时 VM 运行最终 EXE。后者测试长路径安装、逐文件 SHA256、安装目录里的 Harness/Feishu/browser/server smoke、覆盖安装和卸载，核对注册项清理以及用户数据保留。证据写入 `windows-installer-lifecycle.json`，任何失败阻止发布。这项实装测试不能在维护者日常电脑上伪造 CI 环境执行。

Windows/Mac 检出固定 Harness 源码，再构建或复用经过验证的缓存。缓存键含目标 CPU、Harness commit 及相关构建脚本 hash；缓存命中仍验摘要，Mac 还验签名和单 CPU。不要用缓存命中替代完整验证。

### 5.3 Mac 为什么拆成两份

Bot 不再把 arm64 和 x64 塞进同一 Universal 安装包。两台原生 runner 分别生成 thin App/DMG，Node/Electron、Harness、CUA、浏览器和飞书资源按相同 CPU 准备，缓存和 manifest 分开。

Mac 先生成 App，再由专用脚本串行签名、制作 DMG；挂载最终 DMG 检查签名和目标 CPU，再复制到隔离 Applications 目录，逐项校验文件、链接和权限，从安装目录运行依赖与服务检查，并测试替换和删除。这避开了历史并行签名导致的文件句柄耗尽。已锁定摘要的 Harness/飞书资源不随意重签。

**这是 Bot 内置 Harness 的分架构交付，不是修改独立 Harness 产品的 Universal 发布流程。** 一次 `platforms=macos` 或 `all` 即可并行生成两包，不要求人工运行两次。

### 5.4 Linux 新接入部分

Linux 在 runner 中装 Xvfb、D-Bus、FUSE、GTK 等依赖，在虚拟显示环境下构建和验证。现有验证脚本会在隔离 runner 安装/升级实际 DEB，检查 `/opt/OpenMausBot`、浏览器、服务和 Linux 生命周期，再清理测试安装。

Linux 当前跳过 Windows/Mac 专用 Harness 和飞书运行时准备；平台能力不能按 Windows/Mac 完全等同宣传。本轮 Linux 构建和已有自动门禁已实际通过；这不表示 Linux 拥有内置 Harness 或已完成人工业务验收。

### 5.5 publish：先校验，再对用户可见

- 从同一个 Run 下载 `release-*` 已验证产物；校验同版本、同 source SHA、同 toolkit tree 和完整的平台集合。
- 生成 `BUILD-MANIFEST.json`、`SHA256SUMS.txt`，上传安装包和两份审计附件到草稿。
- 对远程附件再检查文件名、数量、uploaded 状态、大小和 GitHub 返回的 SHA256 digest。
- 校验标签与实际构建源码的对应关系。正式发布 PATCH 明确带上 `tag_name` 和 `target_commitish`，防止草稿被发布成 `untagged-...`。
- `release` 将 draft 改为 false、prerelease 改为 false、make_latest 设为 true；`prerelease` 不设 Latest；`draft` 停在草稿；`artifacts` 不创建 Release。

内部工具只认识 artifacts/draft/prerelease 等模式，因此 YAML 把需要远程发布的模式先映射为 draft，再由最后的独立步骤完成正式发布。不要直接给底层工具新增 `RELEASE_MODE=release` 而不改工具实现。

## 6. 产物保存、校验与发版验收

### 6.1 Actions Artifact 与 Release 是两层东西

| Artifact 名称 | 内容 | 保留期 |
| --- | --- | --- |
| `release-preflight-<runId>` | 前置检查报告（若已生成） | 30 天 |
| `candidate-<target>-<runId>` | 自动验收前保存的候选包 | 14 天 |
| `release-<target>-<runId>` | 自动验收通过的包与平台 manifest | 30 天 |
| `evidence-<target>-<runId>` | 诊断证据（各平台内容不完全相同） | 14 天 |
| `release-manifest-<runId>` | 汇总 manifest 与 SHA256SUMS | 30 天 |

保留期来自当前 YAML，可能受组织策略限制。候选上传成功不等于验证通过；Artifacts 不会自动出现在 Releases。发布失败时若汇总文件已生成，最后的 always 上传步骤会尽量保留它们。完整错误日志首先看 Actions Job log。

### 6.2 下载并校验

从 Release 下载到一个新的空目录，避免和旧包混合。以下 PowerShell 示例会实际下载附件，版本按需替换：

```powershell
$Repo = 'AI-Applications-Team/OpenMausBot'
$Tag = 'v0.1.86'
$Dest = Join-Path (Get-Location) "release-check-$Tag"
if (Test-Path -LiteralPath $Dest) { throw '请改用新的空目录' }
New-Item -ItemType Directory -Path $Dest | Out-Null
gh release download $Tag --repo $Repo --dir $Dest
if ($LASTEXITCODE -ne 0) { throw '下载失败' }
Get-Content -LiteralPath (Join-Path $Dest 'BUILD-MANIFEST.json')
Get-Content -LiteralPath (Join-Path $Dest 'SHA256SUMS.txt')
```

逐文件按 SHA256SUMS 验证，不只核对文件大小：

```powershell
$CheckRoot = [IO.Path]::GetFullPath($Dest).TrimEnd([IO.Path]::DirectorySeparatorChar)
foreach ($Line in Get-Content -LiteralPath (Join-Path $CheckRoot 'SHA256SUMS.txt')) {
  if ($Line -notmatch '^([a-fA-F0-9]{64})\s{2}(.+)$') { throw '摘要格式不正确' }
  $Expected = $Matches[1]
  $Name = $Matches[2]
  $File = [IO.Path]::GetFullPath((Join-Path $CheckRoot $Name))
  if (-not $File.StartsWith($CheckRoot + [IO.Path]::DirectorySeparatorChar, [StringComparison]::OrdinalIgnoreCase)) { throw '摘要路径越界' }
  $Actual = (Get-FileHash -LiteralPath $File -Algorithm SHA256).Hash
  if ($Actual -ne $Expected) { throw "哈希不一致：$Name" }
  Write-Output "PASS $Name"
}
```

SHA256SUMS 当前列的是安装包摘要；两份审计文件自身的上传摘要由 workflow 对远程 API 返回值另行核验。恢复发布时不要只凭 SHA256SUMS 一项就跳过 manifest 来源和平台完整性核验。

### 6.3 发布完成的判断标准

- Release 标签是预期的 `v<version>`，正式版不是 Draft/Prerelease，Latest 指向预期版本。
- manifest 的 `version`、`sourceSha`、`run` 与 prepare / build 证据一致，选定平台都标为 `automatedVerification: passed`。
- `all` 有四个平台、五个安装包和两份审计文件；`desktop` 有三个安装包和两份审计文件。
- 安装包与上传摘要一致；Windows、两种 Mac、Linux 的测试责任人分别记录结果。
- 企业流程当前只提供 Release 手动下载更新，**没有自动更新 feed**。Latest 只是 GitHub Release 标记，不等于客户端能自动更新。

## 7. 失败怎么处理：先找到最早失败步骤

### 7.1 快速排查表

| 现象 / 报错 | 优先检查 | 合理处理 |
| --- | --- | --- |
| 找不到新选项 / 仍默认 desktop 或 artifacts | Use workflow from 是否为旧 main/旧提交 | 选包含 8538face 的 workflow 分支；源码也要匹配 |
| 缺脚本、Unknown release mode | 只复制了 YAML，源码过旧，或直接给底层传 release | 检查完整提交和 mode 映射，不随意跳过检查 |
| 创建 Release / 标签 403 | 发布 Secret、所属账号、Contents/Workflows 权限、组织规则 | 更新授权或同名 Secret；不要假设 GITHUB_TOKEN 足够 |
| Harness checkout 404 / Repository not found | 私库读取 Secret、组织访问、固定 commit/子模块 | 修复只读访问；不要改为拉 latest |
| 版本已存在 | 已发布 Release、隐藏草稿、已有不同 SHA 的 tag | 已发布版本用新版本号；草稿按下节恢复；不移动历史 tag |
| artifacts 版本不一致 | package.json 与输入 version | 先提交正确版本，或用 draft/release 候选机制 |
| vendor 下载/校验失败 | 固定 URL、大小、SHA256、网络、下载源是否仍存在 | 修复来源或重试；升级资源必须同步锁定信息，不能取消哈希校验 |
| Yarn immutable / file: 依赖异常 | 固定 Harness 源码和平台锁图 | 保留现有稳定化两遍、registry pin 比对和恢复锁文件逻辑 |
| Windows EPERM / 临时目录占用 | cloudflared 清理重试、文件锁、日志首错 | 保留已实现的有界重试；不要全局关安全软件或清空用户目录 |
| Mac EMFILE、codesign / CPU 失败 | 串行签名、ulimit、原生 runner、缓存 CPU | 不恢复 Universal 混装；不以跳过签名检查解决 |
| Artifact not found | 之前是否已经 build/verify 失败 | 先修最早失败，不能把缺产物误判为应用依赖缺失 |
| publish 失败但 build 全绿 | 草稿状态、附件上传、token、hash/source/platform 校验 | 保留已验证包，按恢复步骤处理，别直接重打一遍 |
| 安装很慢 / Harness 启动失败 | 旧 NSIS 长路径漏文件、额外复制、大量散文件 | 见第 8 节；核对是否下载了新修复候选，而非原 v0.1.85 附件 |
| 卸载没进度 / 覆盖安装失败 | 旧 one-click 静默卸载、父安装器目录锁或组件文件占用 | 新 assisted 页面与定向进程清理；查看 `%TEMP%\RuijieBot-installer.log` 和生命周期证据 |

### 7.2 哪些情况可以重试

还没创建 Release 草稿、且只是 runner/网络临时错误时，可在**同一个 Run**选择 Re-run failed jobs，保留已成功平台的产物。重试仍可能遇到 immutable Artifact 同名冲突；出现此类错误时先检查已存在的 Artifact，不要凭文件名删包或混装。

如果修改了源码或 workflow，必须从包含修复的新提交重新 Run workflow；Re-run 使用原 workflow 提交，不会自动捡到新修复。如果已经有公开 Release，修源码后正式发布使用新版本号；同显示版本的排错候选只能用 artifacts，不覆盖旧发布。

**一旦已创建草稿，不要无脑 Re-run publish 或重新触发同版本。** 新 prepare 会拒绝已有草稿，底层 publish 也不是通用断点续传器；它可能因版本存在而失败。先盘点草稿及原产物。

### 7.3 草稿 / 上传失败的恢复清单

1. 记录原 Run ID、prepare 的最终 source SHA、版本、选定平台、Release ID 和失败步骤。workflow 的 `headSha` 在指定 source_ref 或生成版本候选提交时不一定等于最终源码 SHA，以 manifest 和 prepare 为准。
2. 读取带鉴权的 Release 列表。`GET releases/tags/<tag>` 在本次现场可能看不到草稿；不要因此创建第二个同版本草稿。
3. 下载原 Run 的全部 `release-<target>-<runId>` 与 `release-manifest-<runId>` 到独立空目录，保留分平台 manifest。检查来源、完整目标集合、每个自动验收状态和每个文件摘要。不能拿 candidate-* 代替已验收产物。
4. 比对远程草稿附件：文件名集合、数量、uploaded 状态、大小、SHA256 digest 都必须一致。只缺文件时上传原验证文件；同名但摘要不同先停止调查，不使用 `--clobber` 掩盖差异。
5. 草稿 target_commitish 应等于最终源码 SHA；若已有 `v<version>` 标签，必须解析到同一提交。不存在标签可在正式发布时由 GitHub 创建；不得把已有不同 SHA 的标签强推改过来。
6. 全部校验完成，并完成该次要求的真人验收后，发布**同一个草稿**。API 修改时显式传 tag_name 与 target_commitish，见下方命令。
7. 再读取 Release 和 Latest，确认没有被发布成 `untagged-...`，附件仍齐全。保留恢复记录，包含“没有重编译”的依据。

只读查询示例：

```powershell
$Repo = 'AI-Applications-Team/OpenMausBot'
gh api --paginate "repos/$Repo/releases?per_page=100" --jq '.[] | {id,tag_name,draft,prerelease,target_commitish}'
$ReleaseId = '替换为要检查的ReleaseID'
gh api "repos/$Repo/releases/$ReleaseId/assets?per_page=100" --jq '.[] | {name,size,state,digest}'
```

原产物下载示例（`$RecoveryDir` 应是新的专用空目录）：

```powershell
$RunId = '替换为原构建RunID'
$RecoveryDir = Join-Path (Get-Location) "recovery-$RunId"
gh run download $RunId --repo $Repo --pattern "release-*-*-$RunId" --dir (Join-Path $RecoveryDir 'platforms')
gh run download $RunId --repo $Repo --name "release-manifest-$RunId" --dir (Join-Path $RecoveryDir 'manifest')
```

下面命令**会正式发布**，仅在上述检查全部完成后执行，不是只读测试；登录身份须有发布权限。`$SourceSha` 来自已核验的 manifest：

```powershell
$Tag = '替换为v开头的目标版本标签'
$SourceSha = '替换为manifest中的40位sourceSha'
gh api --method PATCH "repos/$Repo/releases/$ReleaseId" -f tag_name=$Tag -f target_commitish=$SourceSha -f name="RuijieBot $Tag" -F draft=false -F prerelease=false -f make_latest=true
gh release view $Tag --repo $Repo --json url,isDraft,isPrerelease,tagName,assets
gh api "repos/$Repo/releases/latest" --jq '{id,tag_name,target_commitish}'
```

## 8. 当前质量边界与优先待办

### 8.1 Windows 的三个问题：原因、修复和剩余边界

**初始化失败是安装漏文件，不是用户没登录。** 旧 EXE 的归档中有 getMachineId.js，但安装后的实际路径长达 262 字符，旧 Nsis7z::Extract 将其漏掉且返回成功。日志报 Cannot find module './machine-id/getMachineId'。已用真实 NSIS 最小包稳定复现，再用固定 7za 保留同一长路径；完整原始归档解压后也通过 Harness 全目录摘要及该依赖的实际加载检查。

**安装慢有额外复制开销。** 现场包展开约 1.9 GiB、38,926 个文件，Harness 占绝大多数；旧流程先临时解压，再逐文件复制。固定 7za 完整解压原归档实测 507.84 秒，这是单次解压时长，不能当作新版完整安装时长。新实现直接解压到目标目录，消除额外整包复制；未删除固定依赖，未关闭安全软件，近四万文件的扫描成本仍可能存在。

**看不到卸载进度有明确模板原因。** 旧 one-click 模板在确认后强制 SetSilent silent。新企业配置改用正常进度和完成页面，并显示关闭组件、删除程序文件的阶段；/S 仍用于升级和自动验收。卸载还改为按安装目录核对进程身份，兼容 32 位 PowerShell 查询 64 位进程，不按名称误关独立 Harness 或开发版。

普通 NSIS RMDir /r 可能留下长路径，新实现使用扩展路径前缀、有限重试和残留检查；失败保留卸载入口并记录 %TEMP%\RuijieBot-installer.log。覆盖安装时先释放父安装器占用的旧目录，否则子卸载器会删除文件后卡在目录清理。默认保留聊天、账号和工作区数据。

维护者必须连同 patches/app-builder-lib@26.15.3.patch、pnpm 锁文件、prepare-windows-installer.mjs、NSIS include、进程关闭脚本和验收脚本一起迁移。独立 7za 来自 builder 固定工具集并额外核对可执行文件摘要，已包含许可；用户不需要另装 7-Zip。

当前本地证据：小型真实 NSIS 回归通过；实际 electron-builder 生成的独立小包已完成安装、覆盖安装和卸载，保留了 343 字符的文件路径；错误安装标记会被拒绝，独立进程和测试数据被保留。完整 Windows 修复候选 Run 35586637648 及本轮四平台 Run 35589546915 均已通过各自验收。旧 v0.1.85 附件保持原始字节；请下载新 v0.1.86。

### 8.2 自动验证覆盖不到的事项

旧 Windows verify 只验证 `win-unpacked` 和签名状态，漏测了安装解压路径；新流程已增加最终 EXE 的实际安装/覆盖安装/卸载与耗时记录。CI 的静默验收仍不能代替不同用户机器上的可见界面、慢磁盘、安全软件和真人账号业务验收。

Mac 已通过最终 DMG 挂载验签、复制安装、安装目录运行、替换和删除自动检查；真实账号登录、Keychain、屏幕录制/辅助功能等 TCC 权限，以及真实历史用户数据的覆盖升级仍需真人测试。Windows 未签名，Mac 只有 ad-hoc 签名、没有 Developer ID 公证；Release 正式可见不意味着已完成商业签名。

应用验收要保留本轮设计：Grok Bot 风格简洁界面；执行电脑入口在输入栏；模型在 Bot 编辑资料中设置；不恢复杂乱右栏；保留图片搜索展示与文件预览；验证记忆草稿保护、失败恢复及电脑连接反馈。Harness 保持 2.1.10 与配套 CLI，Mac 两份包不能互相混入对方 CPU 资源。

### 9.4 本地修改与验证的最短路线

先在正确维护基线新建任务分支（例如 fix/composer-spacing），不要在别人正在使用的开发目录上清理或覆盖。安装依赖使用锁定版本，以下检查按改动范围选用：

```powershell
corepack enable
corepack pnpm install --frozen-lockfile
corepack pnpm typecheck
# 输入框/字号/记忆相关改动的针对性回归
corepack pnpm exec vitest run src/lib/cn.test.ts src/lib/composer-runtime-state.test.ts src/lib/memory-editor.test.ts

```

### 9.5 从修改到下一版，按这个顺序收口

1. 看 git status 与 diff，只提交本任务的源码、对应测试、需要的锁文件/补丁和说明；不提交 .env、token、用户配置、node_modules、release 大包或个人临时产物。
2. 将任务分支推到**目标仓库**。个人副本和公司不是自动双向同步；在个人 main 修好不代表公司维护分支也有该修复。
3. 用新提交发起验证。只改应用时可选择现行 workflow 分支并把 source_ref 固定为任务提交；若修改 YAML，Use workflow from 也必须选包含新 YAML 的任务分支。两者必须包含配套脚本。
4. 下一正式版本明确填未占用的新号（例如 0.1.87），选择 all；需要先人工验收用 draft，正常自动发布用 release。若临时选 artifacts，version 必须与该源码 package.json 一致；它不会替你升级版本或自动晋级旧产物。
5. 失败先看第一个失败任务；修源码后发起新 Run，不用旧 Run 的 Re-run 冒充新源码。发布收尾失败则优先核对同一批已验收产物和草稿，按第 7 节恢复。
6. 确认所有平台、manifest、远程附件和所需人工验证后，将审核通过的代码合入对应维护分支；公司是否最终合入 main 由维护团队决定。不要移动已经发布的版本标签。
7. 保存本轮 Run、Release、最终源码 SHA、安装包摘要及验证边界，更新本文。workflow 自动准备的版本提交不会替团队推进维护分支的 package.json，后续要明确选择是否同步版本字段。

如果升级 Harness，先审查目标 Harness 源码与 CLI，再同步 shared/ruijie-harness-release.ts、workflow 固定 ref/缓存键及相关准备/校验逻辑，逐平台重验。不能只改一个 2.1.10 字符串、使用 latest 或把 Mac 两种架构塞进同一个缓存。单纯改文档不需要再次构建安装包。
